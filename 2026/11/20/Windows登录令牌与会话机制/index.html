Windows 登录、访问令牌与会话机制

发表于2026-11-20|更新于2026-11-19|基础学习记录
|浏览量:

前言

学习 Windows 安全时，经常会遇到令牌、登录会话、组和特权这些概念。单看定义似乎都能理解，但把它们放进一次登录过程里，就容易混淆。比如，密码验证通过后，进程凭什么访问文件？管理员登录后，为什么普通程序还需要提权？移除组成员，又为什么不一定立即影响已有进程？

这篇笔记从一次密码交互登录开始，顺着凭据提交、身份认证、令牌创建到进程启动的过程，把这些概念串起来。文中也整理了术语表和流程图，方便后续学习时回头查阅。

一、令牌存在的真正原因

我们先来分析一下 Windows 为什么需要令牌。常见的说法是“令牌是权限的载体”，但这句话没有解释为什么需要令牌。

访问文件时，系统既要知道是谁在访问，也要知道对方申请了什么权限。登录认证解决的是身份验证，访问令牌则把用户 SID、组 SID、特权等信息组织成一个安全上下文，供后续操作使用。

进程通常有一个主令牌；线程模拟其他用户时，还可能有模拟令牌。系统进行访问检查时，会选用相应的令牌，再结合对象的安全描述符、请求的访问权限等信息作出判断。

信息 在访问检查中的作用
用户和组 SID 与对象 DACL 中的访问控制项匹配
特权及其启用状态 在适用操作中参与权限判断
完整性级别 参与强制完整性检查，例如限制低完整性进程写入较高完整性对象

因此，可以把令牌理解为供程序使用的安全上下文。它让后续访问检查能够使用认证后建立的身份与权限信息，而具体资源是否允许访问，仍要在检查时判断。这里涉及的 DACL、SID 等术语，下面会逐一解释。访问令牌 · 访问检查过程

二、登录时到底发生了什么

了解令牌承担的功能后，我们再来梳理登录和获取令牌的流程。

以下以传统的密码交互登录为例，从三个角度梳理 Windows 的登录流程：谁在处理、每一步产出什么以及为什么这样设计。

先看看登录前台、LSASS 与内核访问检查分别处于哪一层：

正式开始前，先把文中用到的术语列在这里，后面遇到时可以回头查。

Token（访问令牌） 描述进程或线程安全上下文的内核对象，包含用户和组 SID、特权等信息。

SeChangeNotifyPrivilege / SeTcbPrivilege 分别涉及绕过遍历检查等行为，以及作为操作系统的一部分执行可信操作。
SeIncreaseQuotaPrivilege 调整进程内存配额相关的特权；CreateProcessAsUser 等调用通常涉及它。

LOGON_NETCREDENTIALS_ONLY / runas /netonly 与仅在网络访问时使用另一身份的模式有关；本地身份及登录会话行为需按具体接口说明理解。
SeAssignPrimaryTokenPrivilege 涉及为进程分配主令牌；是否需要它取决于具体 API 和令牌使用场景。
UAC / deny-only / 完整性级别 UAC 是用户账户控制；deny-only 表示组 SID 只参与拒绝访问匹配；完整性级别用于强制完整性控制，常见有 Low、Medium、High、System。
登录会话 / LUID 登录会话记录某次认证建立的安全上下文；LUID 是本地唯一标识符，可用来标识登录会话。
Session ID / RDP Session ID 标识 Windows 会话；RDP 是远程桌面协议。会话号并非固定分配，也不同于登录会话的 LUID。
SSO / Credential Guard / VBS SSO 是单点登录；Credential Guard 利用基于虚拟化的安全（VBS）隔离保护部分凭据材料。
SECURITY hive / HKCU 前者是包含本地安全策略等数据的注册表配置单元；HKCU 是当前用户注册表分支的缩写。
句柄 / 引用计数 / 对象管理器 句柄用于访问系统对象；引用计数参与对象生命周期管理；对象管理器负责内核对象的统一管理。
CreateProcess / CreateProcessAsUser 前者通常在调用进程的安全上下文中创建进程；后者使用指定的主令牌创建进程。
CreateProcessWithLogonW / CreateProcessWithTokenW / runas 前两者分别使用提供的凭据、已有令牌创建进程；runas 是以另一身份运行程序的命令，具体行为还取决于选项。
OpenProcess / Mimikatz OpenProcess 获取进程句柄；Mimikatz 是安全研究工具，包含凭据和令牌相关功能，能否使用取决于权限及系统防护。
黄金票据 / 白银票据 / Pass-the-Token 分别涉及伪造 TGT、伪造特定服务票证，以及复用已有访问令牌；实际效果受密钥、验证和权限条件限制。
Domain Admins / Enterprise Admins / Administrators 分别为域管理员组、林级企业管理员组和管理员本地组；作用域和权限授予位置不同。
Backup Operators / Service 前者是备份操作员组；后者表示服务登录相关的特殊身份。
Everyone / Authenticated Users 分别为 Everyone 和通过身份认证的用户相关组；匿名等特殊情况需要单独考虑。
INTERACTIVE / NETWORK / This Organization 按登录方式或认证来源出现的特殊 SID；分别关联交互登录、网络登录以及从本组织认证的身份。

术语说明参考微软的 Windows 认证流程、访问令牌、安全主体和 SSPI 架构。

第一步：在 LogonUI 输入密码，由 Winlogon 传递凭据

用户在 LogonUI 中输入密码后，凭据经由 Winlogon 传递，进入后续认证流程。

这里需要补充一点，Winlogon 负责协调，凭据验证由 LSA 及相关认证包处理。凭据提供程序负责收集和序列化凭据，后续通过系统认证接口提交给 LSA。ALPC 是 Windows 提供的一种本地进程间通信机制，可以参与系统组件间的通信，但不能据此把整个登录链路简化为一个 ALPC 端口。

本地通信的安全性取决于端口的访问控制、调用者身份及服务端校验。由内核实现通信机制，并不意味着所有普通进程都必然无法连接任何相关接口。

这也解释了为什么凭据的收集、传递和保存需要分别保护。Credential Guard 利用 VBS 隔离部分凭据材料，减少操作系统被攻陷后受保护秘密被提取的风险；它的保护范围还取决于凭据类型和使用场景。Windows 认证流程 · Credential Guard 原理

第二步：LSASS 里的 LSA

LSASS.exe 是一个用户态进程，以 SYSTEM 运行——这点很重要，它并不是内核组件。与它相关的组件和数据包括：

模块 职责
LSA 协调认证请求、管理安全策略和登录会话、组织令牌所需的信息
SSP 认证包 可插拔的身份验证模块：kerberos.dll、msv1_0.dll（NTLM）、Negotiate（协商）、negoexts.dll（协商扩展）、wdigest.dll
SAM 本地账户数据库（对应注册表 SAM hive，由 SAM 服务保护）
Netlogon 到域控的安全通道（域登录用）
登录会话及认证状态 关联登录身份与认证状态，相关认证包可维护后续 SSO 所需的凭据材料

这里需要区分认证与授权。

认证确认身份，传统 Windows 登录由 LSA 和相关认证组件参与处理。访问受保护的内核对象时，SRM 等机制依据令牌和对象安全信息执行访问检查。

已有令牌使本地对象访问检查通常无需重新提交密码或联系域控。应用也可以另行执行自己的授权逻辑，访问远程服务时还可能发生新的认证。

第三步：认证包分岔——本地还是域

那么，LSA 拿到凭据后，会把认证请求交给谁处理？

本地账户登录时，由 MSV1_0 处理认证请求，根据用户输入的密码计算 NTLM hash，再与 SAM 中存储的数据进行比对。

域账户在线登录时，通常优先使用 Kerberos；在适用条件下也可能使用 NTLM。域控不可达时，如果本地已有可用的域登录缓存且策略允许，可以使用缓存的登录信息完成本机登录。这与在线认证时的协议回退是两回事，也不保证能访问需要域验证的网络资源。缓存域登录说明

域认证中，用户和组信息的传递方式与认证协议有关。

对比项 Kerberos 域账户的 NTLM 认证
授权相关信息 Windows 域环境中，票证可携带包含用户和组信息的 PAC 域控返回的认证验证信息可以包含用户和组信息
后续处理 服务端按协议处理票证和 PAC，并结合本地信息建立安全上下文 接收方使用返回的验证信息，并结合本地信息建立安全上下文
通信次数 取决于票证缓存、目标服务和实际协议流程 取决于认证方式及实际协议流程

因此，不能简单理解成「NTLM 认证成功后一定要再单独查一次组」。域控的验证响应本身就可以带回相关信息。微软 NTLM 登录协议说明

PAC（Privilege Attribute Certificate） 是携带授权相关信息的数据结构，可以放在 Kerberos 票证中。PAC 的校验涉及服务端签名、KDC 相关签名等机制，使用的密钥和具体校验要求取决于票证及协议场景。把它概括成「都由 krbtgt 密钥签一次」会丢失这些区别。微软 PAC 服务端签名规范

这也是理解票证伪造风险的基础。

  • 黄金票据涉及使用泄露的 krbtgt 密钥伪造 TGT，后续效果受密钥有效性、票证验证和域配置等条件限制。
  • 白银票据涉及使用泄露的服务账户密钥伪造针对相应服务的票证，能否生效还取决于服务端及 PAC 验证等条件。

二者都说明，保护长期密钥和正确验证票证十分重要。

第四步：拿到用户 SID

SID 用来标识用户、组等安全主体。本地或域账户常见的格式是 S-1-5-21-<计算机或域标识>-<RID>，其他类型的身份可以使用不同格式。

  • 本地账户的 SID 可从 SAM 账户信息取得。
  • 域账户的 SID 可由域认证结果提供，例如 PAC 或 Netlogon 返回的验证信息。
  • SYSTEM 使用固定的 S-1-5-18；内置 Administrator 账户通常使用以 -500 结尾的账户 SID，其前缀取决于所在计算机或域。
  • S-1-5-11 表示 Authenticated Users，关联通过认证的身份，不能把它解释为包括匿名身份在内的所有人。

账户改名通常保留原来的 SID；删除账户后新建同名账户，则会分配新的 SID。因此，旧 ACL 中针对原账户 SID 的授权不会自动转给新账户，新账户仍可能通过组等其他授权获得访问权限。微软 SID 说明

已有令牌中的组成员信息通常不会随 AD 组成员变更自动刷新，因此移除组成员后，还要考虑已有会话和令牌的影响。这里没有统一的“十五分钟”有效期，具体取决于令牌、票证、会话和服务的行为。

第六步：由组推导特权列表

特权由安全策略授予用户或组。 本地安全策略可以配置这些分配，域组策略也可以对其施加影响。系统结合用户及其组成员关系，形成令牌中的特权列表。

特权 作用示例
SeDebugPrivilege 在适用条件下调试、访问其他进程
SeBackupPrivilege 以备份语义访问对象
SeImpersonatePrivilege 认证后模拟客户端
SeShutdownPrivilege 关闭本地系统

具体授予哪些主体，要查看目标机器的有效策略，不能把某一组默认值套用到所有 Windows 系统。令牌中持有一项特权，也不意味着该特权当前已经启用。

在常见的 UAC 管理员批准模式下，管理员交互登录会得到完整令牌与过滤令牌。具体行为受账户类型和 UAC 策略影响。

完整令牌 过滤令牌
管理员组 正常启用 标记为 deny-only（仅拒绝）
完整性级别 High Medium
特权列表 包含策略授予的管理特权，启用状态因特权而异 移除部分管理特权，具体内容取决于配置

在上述模式下，桌面 shell 通常使用过滤令牌。

“仅用于拒绝”表示该组 SID 在 DACL 检查中仍可匹配拒绝项，但不能用于匹配允许项。其他 SID 和权限机制仍可能影响最终访问结果。

第七步：铸造 Token

前面的步骤是为了理解而拆开的，实际登录中有些处理会交织进行。认证与策略处理得到相关信息后，系统创建访问令牌。主要信息包括：

填入 来源
User SID 第四步
Group SIDs 第五步（含 deny-only 标记）
Privileges 第六步
Integrity Level 与令牌类型、账户和策略有关，常见有 Medium、High、System 等
Logon Session LUID 关联的登录会话标识；令牌复制并不必然新建登录会话
Session ID 所属 Windows 会话的编号，不能按控制台或 RDP 固定推定

这里需要区分令牌、登录会话和凭据材料。

令牌是受访问控制保护的内核对象。 操作它需要相应的句柄访问权限，某些操作还要求额外特权。例如，AdjustTokenPrivileges 可以调整令牌中已有特权的启用状态；它不能为令牌添加原本没有的特权。是否需要 SeTcbPrivilege 要看具体操作。令牌 API 说明

登录会话关联身份认证状态，凭据材料则由相关认证组件维护。 材料的类型、保存位置和可提取性取决于登录方式、系统配置及保护机制。启用 Credential Guard 后，部分秘密由隔离的 LSA 进程保护，不能笼统说它们都以可读形式保存在普通 LSASS 内存里。

LSASS 因而是凭据保护的重要对象，但「具有 SeDebugPrivilege，就一定能读出所有凭据」也不成立。LSA 保护、Credential Guard 等机制会影响进程访问和秘密提取。LSA 保护 · Credential Guard 原理

第八步：explorer.exe 启动

交互登录完成后，系统建立用户环境，并通过 userinit.exe 等组件启动配置的 shell，通常是 explorer.exe。用户配置加载、登录脚本和 shell 启动等处理涉及多个组件，这里只保留简化后的关系。

在常见 UAC 管理员批准模式下，可以这样理解：

普通桌面程序通常使用标准用户安全上下文，常见完整性级别为 Medium。应用可以通过显式“以管理员身份运行”或请求提升等路径获得管理上下文，浏览器等程序也可能为子进程创建受限上下文。UAC 机制说明

CreateProcessAsUser 是使用指定主令牌创建进程的 API。其权限要求取决于调用场景，通常涉及 SeIncreaseQuotaPrivilege，某些情况下还需要 SeAssignPrimaryTokenPrivilege，不能概括为所有调用都必须拥有后者。API 文档

第九步：子进程继承

CreateProcess 创建的新进程通常在调用进程的安全上下文中运行。即使调用线程正在模拟其他用户，新进程也默认使用调用进程的上下文；若要使用另一个用户的令牌，需要采用适当的进程创建接口。这里描述的是安全上下文的延续，不应据此断言所有进程始终共享同一个令牌对象。CreateProcess 文档

不同进程创建方式的区别如下。

方式 使用的身份或令牌 登录会话方面的注意点
CreateProcessAsUser 指定的主令牌 通常使用令牌关联的既有登录会话
CreateProcessWithLogonW 提供的凭据，行为受标志影响 可建立新登录会话；仅网络凭据模式有不同的本地身份语义
CreateProcessWithTokenW 指定的主令牌，行为受标志影响 不能一概写成不新建会话；文档列出的 LOGON_NETCREDENTIALS_ONLY 涉及新建 LSA 登录会话
runas 依命令选项指定身份 应区分普通用法和 /netonly 等选项

“复用令牌”和“是否新建登录会话”需要结合调用参数分析，审计事件也要另行判断。启用进程创建审计时，新进程可以产生 4688 事件。因此，Pass-the-Token 不能仅凭“使用已有令牌”就推导出“不会留下日志”。CreateProcessWithTokenW 文档 · 进程创建审计

小结

把整个过程串起来，可以得到下面这条主线。

令牌让身份认证的结果能够供后续操作使用。已有令牌的组成员信息通常不会随账户配置自动刷新，但令牌中的部分状态可以通过相应 API 调整，对象 DACL 的变更也会影响后续访问检查。禁用账户、移除组成员或修改密码，都不能简单等同于立即终止所有既有会话。

登录会话的 LUID 与 Windows 会话的 Session ID 分属不同概念。分析一个进程时，需要分别看它使用什么令牌、关联哪次登录，以及位于哪个 Windows 会话。

最后，SSO 所需认证材料的保存方式要结合认证类型和保护机制理解。Credential Guard 利用隔离环境保护部分秘密，符合条件的新版本 Windows 还可能默认启用它。判断机器的实际风险，应核对其配置和保护状态。Credential Guard 与默认启用条件

结语
